## 0. 一句话定位

让不懂 SQL 的业务方**用中文问出准确的数**，并且**能解释这个数为什么这么算**。

核心不是"把自然语言转成 SQL"，而是**把自然语言对准企业已经定义好的指标口径**。NL2SQL 只是最后一步的渲染。

### 0.5.2 为什么 4.0% 是采集偏差，不是市场偏差

**（a）三源覆盖不到 P3 的真实买单方**

| 来源 | 条数 | 它擅长覆盖的岗位 | 它覆盖不到的 |
|---|---|---|---|
| 腾讯招聘（社招） | 228 | 互联网平台 / 游戏 / 广告 / 云 | 券商、基金、银行、咨询、零售与制造业的经营分析岗 |
| 实习僧（校招/实习） | 161 | 大厂实习、校招 | 社招口径的数据分析工程岗 |
| 猎聘 | 9 | 理论上覆盖社招全行业，但本次仅入库 9 条 | 金融/咨询的分析岗几乎没抓到 |

数据分析 Agent 的付费方恰恰在"金融、咨询、零售、制造业经营分析"——这三源对它系统性覆盖不足。**用这批样本算 P3 的市占率，分母本身是错的。**

**（b）反向校验：同一个偏差在 P6 上表现为"虚高"**

| 场景 | 占比 | 为什么是这个数 |
|---|---|---|
| P6 Agent 平台与 Harness | **34.2%**（136 条） | 平台/基建岗高度集中在互联网大厂，被三源完美覆盖 → **虚高** |
| P3 数据分析与经营洞察 | **4.0%**（16 条） | 分析岗分散在各行业业务部门，被三源漏采 → **虚低** |

> 4.0% 与 34.2% 是**同一个采样偏差的两面**：一个被放大，一个被缩小。所以 4.0% **不能反推"这不是真场景"**，只能推出"这不是本校招/大厂社招的主赛道"。

**（c）需求真实性的独立证据（不依赖占比）**

- B25-08 一条 JD 里连续列出"找数、取数、写 SQL、建任务、查血缘、排障、指标理解"七类痛点——这是平台方对**取数环节成本**的自我描述，需求真实存在。
- 但它的组织形态是"**平台的一个功能**"（B25-07 直接把 NL2SQL、Agent 化数据开发写进产品路线图），不是"一个独立岗位"。B10-06、B20-08、B21-02 三条也印证同一形态。
- 因此正确结论是：**能力刚需、专岗稀少、交付形态是子模块**。

### 0.5.3 若要做，做什么（三句话结论）

1. **真正值钱的是语义层与指标口径统一，不是 NL2SQL。** 依据：B07-06 要求"明确指标定义、计算口径、维度及数据血缘"；B25-08 把"指标理解"列为第一类痛点；B11-10 把"结合数据仓库 / 指标体系"写在 Agent 之前。把"销售额"钉成 3 个互斥指标并固化血缘，比把准确率从 70% 刷到 80% 更难被替代。
2. **第二值钱的是"自然语言 → SQL"的正确性验证（而非生成）。** 依据：B11-10 把"构建评测集与自动化评测框架、badcase 分析"单列一条职责。v1.0 的 DSL + 编译器两段式、EX 评测、率值陷阱单测，是唯一能**客观证明自己对**的部分。
3. **不值得投的是问答界面与图表生成。** 依据：5 条产品岗（B05-03、B24-06、B25-02、B25-08、B35-06）没有一条把"前端/可视化"写成技术门槛，这块会被 BI 产品直接吞掉。

> **落地建议**：把它做成 P1（口径问答）或 P6（Harness + 评测）主项目里的**数据分析子模块**，简历写成"主项目 + 子模块"；不要单列"Data Agent 独立项目"，因为 7 条工程向证据里没有一条要求"从零建一套问数系统"。

### 1.2 为什么这个场景"值钱"

| 原因 | 说明 |
|---|---|
| **正确性可被硬校验** | SQL 跑出来的数对不对，客观可验证（不像客服满意度那样主观）。企业愿为"数对"付高薪 |
| **失败代价极高** | 一个错误的经营数字可能导致错误决策。JD 反复强调"**口径一致性**"就是因为这个 |
| **技术栈复合** | 需要同时懂数仓（Hive/Spark/Doris）、语义建模、LLM、SQL 优化、权限体系 |
| **可沉淀资产** | 语义层/指标层一旦建成，是全公司复用资产，不是一次性项目 |

> v2.0 修正：上表第 1、2 行的判断仍然成立（P3 的正确性可硬校验、失败代价高），但第 1 行推导出的"所以薪资最高、值得优先做"这一策略结论**不成立**——样本量太小。见 1.5。

### 1.3 与新增场景的边界（v2.0 新增）

398 条样本把场景从 7 个扩到 11 个（新增 P8 AIOps / P9 实时环境交互 / P10 营销增长 / P11 专业判断）。P3 与这四者的输入都沾"数据"，最容易被合并，因此用**输入来源 / 输出物 / 失败代价**三维切开：

| 对照 | 输入不同 | 输出不同 | 失败代价不同 | 归档判据（看 JD 动词） |
|---|---|---|---|---|
| **P3 vs P8（AIOps）** | P3 输入是数仓表 + 指标口径 + 维表；P8 输入是 metrics / log / trace / profiler 四类时序信号，要求毫秒级窗口对齐与变更关联（B05-08、B31-01、B31-02） | P3 **只读**：取数、算指标、归因、出洞察；P8 **写生产**：改配置、调参、重启、扩缩容 | P3 错了重算一次，代价是几分钟；P8 错了就是线上故障，且必须自带基线快照与回滚 | JD 出现"处置 / 自愈 / 回滚 / 变更"→ P8；出现"取数 / 口径 / 归因 / 报表"→ P3。详见 1.4 |
| **P3 vs P9（实时环境交互）** | P3 的数据是**历史沉淀**（T+1 或流批，允许秒级延迟）；P9 的输入是**当下状态**（屏幕像素 / 传感器 / 车机总线，B30-01、B33-08） | P3 输出报表、结论、建议，给人看完再决策；P9 输出此刻的动作（车控指令 / 机械臂位姿 / NPC 台词） | P3 错了重算；P9 错了不可撤销，且有硬时延预算（16–50 ms / 10 ms 级） | JD 出现"帧率 / 端侧 / 断网 / 拟人度"→ P9；出现"数仓 / 指标 / BI"→ P3 |
| **P3 vs P10（营销增长）** | P3 看的是**全量历史经营数据**，目的是解释"为什么变了"；P10 看的是**实时投放反馈**，目的是"下一步怎么花钱"（B05-01 广告 Agent、B15-08 营销 Agent） | P3 输出**建议**（"华南渠道 ROI 环比降 12%，主因是素材疲劳"）；P10 输出**绑资金的经营动作**（调预算、改出价、发券） | P3 建议错了，人不采纳即可；P10 动作错了直接烧预算，因此必须有预算上限 + 审批护栏 + 实时止损三件套 | JD 出现"出价 / 预算 / 素材 A/B / ROI 归因"→ P10；出现"经营分析 / 归因 / 复盘"→ P3 |
| **P3 vs P11（专业判断）** | P3 的依据是**客观数据**，谁算都一样；P11 的依据是领域先验 + 个体情况（B36-05 医疗诊断、B35-01 人岗匹配、B34-01 AI4S 实验设计） | P3 输出"数是这个 / 变化来自这里"，结论可被 SQL 复现；P11 输出"我判断为 X + 依据链 + 拒答边界" | P3 错了是决策参考失真（可纠正）；P11 错了要担责（误诊、歧视），责任不可用"重算一次"了结 | JD 出现"诊断 / 匹配 / 实验设计 / 判断"→ P11；出现"指标 / 维度 / 报表 / 归因"→ P3 |

> 一句话记法：**P3 只读历史数据、给建议；P8 写生产系统；P9 控制正在运行的设备；P10 动钱；P11 下结论并担责。**

### 1.4 P3 与 P8 的血缘与分界（v2.0 新增，本节是 P3 最需要讲清的一段）

**先说血缘：两者共用大半个技术栈。** P3 的"取数 → 算指标 → 归因 → 出结论"和 P8 的"指标异常 → 根因排序 → 处置 → 效果验证"前半段几乎是同一条链路。B05-08（AI Infra 调优 Agent）的闭环原文就是"**性能归因 → 方案生成 → 实验验证 → 收益量化**"——"归因"两个字完全一样。共用件包括：查询网关、指标定义、维度下钻、贡献度分解、权限注入。所以从 P3 转 P8 不是转行，是**在同一个链路上多接一段"执行"**。

**再说分界：只有一条，但这条决定了全部工程差异。**

| | P3 | P8 |
|---|---|---|
| 链路终点 | 停在"告诉人" | 必须"自己动手" |
| 对数据的权限 | **只读**（只读账号 + RLS） | **读写**（要能改配置/调参/重启/扩缩容） |
| 上线前准备 | 评测集跑分 | 评测集跑分 **+ 基线快照 + 回滚预案 + 灰度分批** |
| 验证方式 | 结果对不对（EX / 口径一致性） | 处置后**指标是否真的变好**，且失败自动回滚 |
| 失败后果 | 结论错，重算 | 故障扩大，可能不可用 |

**P8 多出来的三个硬约束，P3 里一个都不存在**：
1. **变更前基线**：处置前必须冻结当前指标快照，否则事后无法证明"是处置起作用还是自然恢复"。
2. **分批灰度**：先 1 台 / 1 个分片，观察窗口内指标不劣化才继续。P3 的查询没有"批次"概念。
3. **闭环验证与自动回滚**：处置后必须在固定窗口内验证效果，未达预期自动回滚——这是"闭环控制"内核，不是"加个审批按钮"。

> 对写简历的直接影响：如果项目里只做到"生成了分析报告、给了建议"，就不能声称有 P8 经验；反之，如果声称做 AIOps 却讲不出"基线快照 / 分批 / 自动回滚"这三件，面试官会判定你只是把 Data Agent 换了个名字。

### 1.5 v2.0 修正：P3 的岗位数量已被 P6 与 P8 分流（推翻 v1 的"优先做"建议）

v1.0 判断 P3 是"薪资带最高的一档"（依据是猎聘 40–70K·14 薪那一条），并据此建议优先投入。398 条重算后，这个策略结论要降级：

| 指标 | v1.0（70 条） | v2.0（398 条） | 变化 |
|---|---|---|---|
| 主场景命中 | 11 | **26** | 绝对数 +136% |
| 主场景占比 | 15.7% | **4.0%** | −11.7 pt，位次降至 **第 6**（P6 136 / P9 32 / P2 24 / P5 22 / P4 20 均在前） |

**两个分流方向，都能在锚点上看到：**

1. **向上被 P6 吸走**——"智能问数"被写成平台的一项能力，而不是一个独立项目。B11-02（腾讯金融科技 Agent 架构师）主场景是 P6、次场景才是 P3；B25-03（腾讯云 TBDS）虽是 P3，但商业化职责占比很高。也就是说：**P3 的内核没有消失，它变成了 P6 平台里的一个工具。**
2. **向下被 P8 吸走**——一旦"指标异常 → 根因 → 处置"闭环里包含写操作，岗位就归 P8。B36-03（工业质检：缺陷根因分析 + 工艺参数调优）被判定表列为 P8 候选，就是因为它落在"分析完要调参"。

**修正后的结论（写进决策时请用这句）**：
> P3 仍然是**技术上最能自证**的场景（SQL 结果对不对，客观可校验，不依赖用户满意度这类主观指标），但它**不是岗位最多的场景**。若目标是岗位数量，应把 P6 痕迹叠在 P1/P2/P5 外壳上；若目标是展示数仓 / 语义层 / 归因的深度，P3 仍是最优载体——只是别再拿"薪资最高、优先做"当理由，那是一条 JD 推出来的。

### 2.1 用户角色

| 角色 | 诉求 | 痛点 |
|---|---|---|
| **业务分析师 / 运营** | "上周华东区退货率为什么涨了" | 要提需求给数据组，排队 2–3 天 |
| **管理层** | "这个月 GMV 完成率" | 只能看固定报表，想下钻要另外提需求 |
| **数据工程师** | 别天天让我写重复的取数 SQL | 60% 时间在响应临时取数 |
| **数据治理** | 口径必须统一 | 同一个"活跃用户"，5 个部门 5 个算法 |

### 2.2 典型任务（五级难度，这是 P3 的核心设计骨架）

| 级别 | 任务类型 | 示例 | 技术难度 | 是否需要 LLM 之外的能力 |
|---|---|---|---|---|
| **L1** | 单指标取数 | "昨天 GMV 多少" | 低 | 指标映射 |
| **L2** | 多维度聚合 | "上周各省份 GMV 排名前 5" | 中 | 维度识别 + 时间口径 |
| **L3** | 同比环比 / 占比 | "本月退货率环比涨了几个点" | 中高 | 时间偏移 + 率值计算（**分母陷阱**） |
| **L4** | 归因分析 | "退货率涨了，主要是哪个品类/渠道贡献的" | 高 | 维度下钻 + 贡献度分解 |
| **L5** | 多步分析 + 报告 | "分析一下 Q3 经营情况，给出问题点和建议" | 极高 | 任务规划 + 多查询编排 + 结论生成 |

> **面试分水岭**：只做了 L1/L2 的，是"NL2SQL demo"；做到 L3/L4 的，才叫 Data Agent。L4 的贡献度分解（如加法分解、乘法分解、Shapley 近似）是核心加分项。

### 2.3 量化基线

| 指标 | 人工基线 | 目标 |
|---|---|---|
| 临时取数响应时长 | 4–48 h（排队） | ≤ 30 s |
| 口径错误率（同一问题不同人算出不同数） | 高（无法度量） | 0（语义层强制统一） |
| 取数需求自助化率 | 20% | ≥ 70% |

```
自然语言问题
   │
   ▼
┌─────────────────────────────────────────────────────────────┐
│ ① 问题理解层                                                  │
│   · 时间解析："上周""本月""近30天""去年同期" → 绝对区间          │
│   · 实体链接：指标 / 维度 / 维度值 / 过滤条件                    │

│   · 问题分类：L1–L5 → 决定后续链路                              │
│   · 歧义检测：命中多指标（"用户数" → 活跃/新增/注册）→ 反问澄清    │
└────────────────────┬────────────────────────────────────────┘
                     ▼
┌─────────────────────────────────────────────────────────────┐
│ ② 语义层（Semantic Layer）——★ 系统的心脏                       │
│   · Metric Registry：每个指标定义「表达式 + 依赖表 + 口径 + 负责人」│
│   · Dimension Registry：维度层级（region > province > city）    │
│   · 口径约束：如"GMV 不含退款""活跃=7日内有登录"                  │
│   · 生成时只允许**引用已注册指标**，不允许 LLM 自由拼 SQL 表达式    │
└────────────────────┬────────────────────────────────────────┘
                     ▼
┌─────────────────────────────────────────────────────────────┐
│ ③ SQL 生成层（受约束生成）                                      │
│   · 模板槽位填充（L1/L2 走模板，不需要 LLM 写 SQL）               │
│   · LLM 生成（L3–L5，输入 = 语义层 DSL + few-shot 示例）          │
│   · 生成物不是裸 SQL，而是 **中间表示（DSL/逻辑计划）**            │
│   · DSL → SQL 由确定性编译器完成（可单测、可审计）                 │
└────────────────────┬────────────────────────────────────────┘
                     ▼
┌─────────────────────────────────────────────────────────────┐
│ ④ 校验层（四道）                                              │
│   a. 静态：表/列存在性、权限、分区裁剪是否命中                    │
│   b. 语义：指标与维度是否可组合（防止"退款率按供应商拆"这种无意义组合）│
│   c. 成本：EXPLAIN 预检，扫描量超阈值 → 拒绝/要求加过滤条件       │
│   d. 结果：空结果/异常大结果/负值率值 → 二次确认                  │
└────────────────────┬────────────────────────────────────────┘
                     ▼
┌─────────────────────────────────────────────────────────────┐
│ ⑤ 执行层                                                      │
│   · 只读账号 + 行级权限注入（RLS）                               │
│   · 查询超时 + 结果行数上限 + 资源队列                            │
│   · 结果缓存（同 DSL hash → 复用）                               │
└────────────────────┬────────────────────────────────────────┘
                     ▼
┌─────────────────────────────────────────────────────────────┐
│ ⑥ 呈现层                                                      │
│   · L1/L2：数字 + 单位 + 口径说明 + 数据更新时间                  │
│   · L3：数字 + 对比基准 + 变化拆解                               │
│   · L4：贡献度瀑布图 + Top 贡献维度                               │
│   · L5：结构化报告（结论 / 依据 / 风险 / 建议）                    │
│   · 全部附「可查看 SQL」与「口径定义」链接（可解释性）              │
└─────────────────────────────────────────────────────────────┘
```

### 关键：为什么要引入中间表示（DSL）而不是让 LLM 直接写 SQL

| 直接写 SQL | 走 DSL + 编译器 |
|---|---|
| 无法保证只用已注册指标 | ✅ 指标必须来自 registry |
| 口径靠 Prompt 约束，不稳定 | ✅ 口径固化在指标定义里 |
| 权限需在 SQL 层解析 | ✅ 编译器统一注入 RLS |
| 难以单测 | ✅ DSL 可断言、可 diff |
| 换数据库方言要改 Prompt | ✅ 只改编译器 |

**这个设计判断是本 PRD 最有价值的一点，也是面试里最容易被追问的地方。**

## 7. 核心难点与解法

### 难点 1：口径一致性（企业最在意、最多人做不好）

**问题**：问"上个月销售额"，Agent 算出 1000 万；财务说应该是 950 万（不含退款）。谁对？

**解法**：
1. **指标唯一化**：`gmv`、`gmv_net_refund`、`gmv_paid` 是三个不同指标，**不许用一个"销售额"模糊映射**
2. **默认口径显式声明**：映射到某个指标时，答案里必须带一句"（口径：含退款前金额，不含运费）"
3. **歧义主动澄清**：当业务词可映射多个指标且置信度差 < 0.15 时**反问**，不猜
4. **口径达标测试**：评测集里专门放 20 题"多口径可解释"的问题，检查 Agent 是否会说清楚自己用了哪个口径

> 口径一致性 ≠ 准确率。准确率是"数对不对"，口径一致性是"**是否用了你以为的那个数**"。后者才是企业真正的痛点。

### 难点 2：率值聚合陷阱（最容易被面试官问倒）

**问题**："各品类退货率" 如果写成 `AVG(退货率)`，结果是错的（大品类和小品类权重相同）。

**解法**：
- 语义层里，**率值类指标只注册"分子 + 分母"两个原子指标**，不注册"率"本身
- 任何率值必须在查询时现算：`SUM(退货数) / SUM(订单数)`
- 编译器层面禁止对率值指标做 `AVG`/`SUM`，只允许 `SUM(num)/SUM(den)`
- 加单测：构造两个规模差 100 倍的品类，验证结果与"正确加权"一致

这个细节讲出来，面试官会立刻判断"这人真跑过数"。

### 难点 3：SQL 生成准确率怎么从 60% 提到 75%+

**分阶段提升路径（可量化叙述）**：

| 阶段 | 做法 | 准确率 |
|---|---|---|
| Baseline | 直接把 schema + 问题给 LLM 生成 SQL | 58% |
| + Schema RAG | 只检索相关表/列（不是全库 schema 塞 prompt） | 66% |
| + 语义层约束 | 指标必须来自 registry，DSL 两段式 | 71% |
| + Few-shot 检索 | 按问题相似度检索 3 条相似 Q-DSL 示例 | 74% |
| + 执行反馈自修正 | 报错后按错误类型定向修复（≤2 轮） | **77%** |

**每一档都要有评测数据支撑**——这是简历上最有说服力的"工程迭代"叙事。

### 难点 4：查询安全与成本

- 只读账号 + 库表白名单（**不给 LLM 全库 schema**，避免它查到不该查的表）
- RLS：编译期把 `WHERE tenant_id = :current_tenant` 注入到每张表的扫描节点
- 成本预检：`EXPLAIN` 后估算扫描行数，超阈值 → 拒绝并提示"请补充时间范围"
- 分区裁剪校验：没带时间条件的查询直接拒绝（这是数仓成本失控的第一大原因）

### 难点 5：L4 归因怎么做（加分项）

**加法分解**（总量 = Σ 各维度贡献）：
```
Δ退货率 = Σ_i (w_i^t × r_i^t) - Σ_i (w_i^{t-1} × r_i^{t-1})
        = Σ_i [ Δw_i × r_i^{t-1} + w_i^{t-1} × Δr_i + Δw_i × Δr_i ]
           └─ 结构效应 ─┘   └─ 水平效应 ─┘   └─ 交互项 ─┘
```
→ 告诉业务："退货率涨 1.2pt，其中 0.8pt 来自**结构效应**（低退货品类占比下降），0.4pt 来自**水平效应**（某品类本身退货率上升）"。

这个"结构 vs 水平"的拆分，是数据分析的真正内核，比"用 LLM 生成一段分析文字"高一个层级。

## 8. 评测体系

### 8.1 离线评测集（≥120 题）

| 分层 | 题数 | 判定方式 |
|---|---|---|
| L1 单指标 | 30 | **执行准确率 EX**：Agent SQL 结果 == 标准 SQL 结果（数值相等） |
| L2 多维聚合 | 30 | 同上（按集合相等比较，顺序无关） |
| L3 同环比 | 25 | 同上（浮点容差 1e-6） |
| L4 归因 | 15 | 主要贡献维度 Top3 命中率 |
| 歧义澄清 | 10 | 是否反问（不许猜） |
| 不可答/越权 | 10 | 是否拒绝（不许硬查） |

### 8.2 关键指标定义

| 指标 | 定义 |
|---|---|
| **EX（Execution Accuracy）** | 结果集与标准答案完全一致的题目占比 |
| **口径一致性** | 答案中显式披露的口径与标准口径一致的题目占比 |
| **有效查询率** | SQL 能成功执行（不报错、不超时）的比例 |
| **平均修正轮次** | 首次生成失败后需要的自修正轮数 |
| **单题成本** | tokens + 查询扫描量折算 |

### 8.3 回归门禁

EX 不得低于上版 -2pt；口径一致性必须 ≥ 0.95；越权拦截 100%。

### 8.4 失败模式分类（v2.0 新增）

「评测」在 398 条 JD 里提及率 **35.4%（141/398）**，是所有单项技能最高，超过 RAG 的 27.1%（`03-能力矩阵/招聘能力要求矩阵-v2.md` §2.5）。P3 有个天然优势：**判分可以完全自动化**——用标准 SQL 跑真值，比对结果集即可，不需要人工标注"答案好不好"。但这也意味着"只报一个 EX"没有信息量，必须报**错在哪一层**。固定 9 类：

| 代码 | 失败模式 | 判定信号 | 修法 | 典型占比 |
|---|---|---|---|---|
| `ENTITY_MISS` | 指标/维度没识别出来 | 实体链接置信 < 阈值；或落到"未注册指标" | 补指标别名表（"销售额"→`gmv_paid` 的候选集）；同义词进 registry | 20–25% |
| `METRIC_AMBIG` | 有歧义但没澄清，猜了一个 | 多候选置信差 <0.15 却直接执行 | 强制反问（FR-3.6）；把"猜对"也算失败——因为不可复现 | 10% |
| `TIME_WRONG` | 时间区间算错 | 与标准答案的区间不重合 | 时间解析单测（20 种表达）；财年/时区显式建模 | 10–15% |
| `DSL_WRONG` | 逻辑计划错（维度/聚合错） | DSL 结构 diff 出差异（缺 group by、多 join） | few-shot 检索相似 Q-DSL；DSL 层单测 | 20% |
| `RATE_TRAP` | 率值聚合错（对率求平均） | 结果与加权真值偏差 >1% 且分母不一致 | 只注册分子/分母；编译器禁 AVG(率)（见 7 难点 2） | 5–10%，**但最致命** |
| `EXEC_ERROR` | SQL 执行报错未修复 | 报错且自修正 2 轮后仍失败 | 按错误类型定向修复（列不存在→检索 schema；类型不匹配→加 cast） | 8–12% |
| `EMPTY_MISREAD` | 空结果直接当 0 回答 | 返回 0 行却回答"为 0 / 没有" | 区分"真无数据"与"过滤条件过窄"，提示可能原因（FR-3.14） | 5% |
| `UNDISCLOSED` | 口径未披露或披露错 | 答案无口径说明，或说明与 registry 不一致 | 口径说明由代码从 registry 拉取，不由 LLM 生成 | 5–8% |
| `OVER_BLOCK` | 该查却被拦 | 权限/成本校验误杀合法查询 | 放宽阈值 + 给出"请补充时间范围"类可操作提示 | 3–5% |

> 这张表就是 P3 最值钱的面试材料：**任何人都会说"我的 EX 是 77%"，只有跑过的人才知道剩下 23% 里 `ENTITY_MISS` 和 `DSL_WRONG` 各占两成。**

### 8.5 P6 特征补齐清单（v2.0 新增）

**为什么必须有**：398 条 JD 中 P6（平台 / Harness）主场景 **136 条 / 34.2%**，11 场景最高（`场景收敛分析报告-v2.0.md` §2）。报告明确 P6 不该当简历主项目，但**任何业务项目都必须带 P6 痕迹**，否则判为"只会调 API"。P3 的 P6 痕迹比 P1/P2 更容易做实——因为它本来就有编译器、单测、评测集这些"平台件"。

| # | 特征 | JD 依据 | 最小实现方式（P3 版，1–2 天） |
|---|---|---|---|
| 1 | **Trace / 可观测** | Trace 提及 11.3%（45 条）；B02-06"全链路追踪、延迟拆解" | 每次问数落一条 span：`阶段(理解/澄清/DSL/编译/校验/执行/解释) / 各阶段耗时 / 命中指标与置信 / DSL 指纹 / SQL 指纹 / 扫描量GB / 是否自修正 / 修正轮次`。有它才能回答"慢在编译还是慢在数仓" |
| 2 | **评测集 + 自动跑分** | 评测 35.4%；B03-09 设"评测工程师"岗 | 120 题 → 每题预存标准 SQL 与真值结果 → `run_eval.py` 自动比对（EX 无需人工）。**这是 P3 相对其他场景的最大评测优势，必须讲出来** |
| 3 | **失败模式分类** | B03-05"对 failure mode 有切身体感" | 用 8.4 的 9 类编码自动打标（多数可由 DSL diff / 报错类型 / 结果比对自动判定，不必人工） |
| 4 | **Token / 成本计量** | 上下文 27.1%；B02-10"上下文与成本治理" | **双成本口径**：LLM token（少）+ 查询扫描量（多）。P3 的成本主体是扫描量不是 token——能说清这一点，就比只会算 token 的人高一档。目标：¥/次 = token 成本 + 扫描量 × 单价 |
| 5 | **上下文压缩策略** | Context Engineering 7.8%（31 条） | **不压对话，压 schema**：全库 schema 塞 prompt 是 P3 最大的 token 浪费与最大的错源。做法是 Schema RAG 只检索相关表/列（这一项就带来 EX 58%→66%，见 7 难点 3），few-shot 只取相似度最高 3 条 |
| 6 | **工具调用错误恢复** | 工具调用 32.9%；B03-04"容错性" | SQL 报错按类型定向修复（≤2 轮）；执行超时 → 降级到预聚合表并标注"预聚合口径"；查询被成本校验拦 → 回灌"请补时间范围"给 LLM 重新生成，而不是直接失败 |
| 7 | **可回放** | B03-04"执行轨迹回放" | 回放要锁定三样：语义层版本（指标定义会被人改）+ DSL + 数据快照日期。少锁一样，"同样的问法昨天对今天错"就无法归因 |

> 反例提醒：写"用了 LangChain 的 SQL Agent"不算 P6 特征——LangGraph 提及率 8.0%、LlamaIndex 2.8%，均低于 MCP 的 11.1%（矩阵 §2.1）。被认的是"你自己定的 DSL 契约 + 单测 + 自动判分"。

| 风险 | 形态 | 对策 |
|---|---|---|
| **越权取数** | 分公司员工问"总部整体数据" | RLS 编译期注入；维表权限按用户属性过滤 |

### 10.3 与其他项目的关系

- 与 P1 的关系：语义层的**指标口径说明**可以用 P1 的 RAG 能力回答（"什么叫有效订单"），但**不要**把 P3 做成 RAG 项目
- 与 P6 的关系：P3 的 SQL 执行天然需要**沙箱与权限网关**，可以复用 P6 的成果（如果都做）

### 10.4 一句诚实的判断：P3 是"能力证明型项目"，不是"岗位覆盖型项目"（v2.0 新增）

16 条主场景（4.0%，第 6）意味着：**在这个项目上投入的时间，不会按岗位数量回报。** 它的回报在另一处——P3 是全 11 个场景里唯一能做到"评测全自动、结论可复现"的（标准 SQL 跑真值，程序判分）。这个特性使它成为**面试里最难被质疑的项目**：面试官可以质疑你的客服满意度口径，但无法质疑"77% 的题你的结果集和标准答案不一致"。

所以简历写法要跟着改，三个要点：

1. **别写"我做了一个 ChatBI"**——这是一句 2023 年的话。写"我把取数链路做成了**可被其他 Agent 调用的工具**（MCP / 函数接口），带口径契约与成本闸门"——这是 B25-08（腾讯大数据 PM「把取数、写 SQL、排障封装为数据 Agent 工具」）和 B11-02 的写法，也顺手把 P6 痕迹补上了。
2. **EX 必须配失败结构**——只写"EX 77%"是及格线；写"77%，剩下 23% 里 `ENTITY_MISS` 21%、`DSL_WRONG` 18%，据此补了指标别名表与 few-shot 检索，EX 74→77"才是加分项（见 8.4）。
3. **想往 P8 靠，必须补三件套**——基线快照、分批灰度、自动回滚。缺这三样，把 Data Agent 改名叫 AIOps 会在第二个追问上崩掉（见 1.4）。

> 一句话：**P1/P2 决定你投得进去，P3 决定面试官信不信你真的懂数据。**

### 12.5 场景边界与"被吸收"的判断

**（a）四场景边界矩阵**

| 维度 | P3 数据分析 | P6 平台/Harness | P1 知识问答 | P8 系统诊断 |
|---|---|---|---|---|
| 输入 | 业务数据（订单/用户/商品/退款） | 任务与工具描述 | 文档语料 | 系统信号（Metrics/Logs/Trace/Profiler） |
| 输出 | 指标值 + 归因 + 建议 | 运行时 / 沙箱 / 评测 / 工具注册 | 答案 + 引用 | 根因 + **处置动作** |
| 是否写 | ❌ 只读 | 提供"能写"的能力，不自己写 | ❌ | ✅ 改生产环境并承担后果 |
| 成功判据 | EX、口径一致性、归因命中 | 任务成功率、时延、成本 | 召回率、忠实度 | 故障是否被定位/恢复 |
| 关键锚点 | B11-10、B25-08 | B20-08、B25-07 | B07-06（口径解释） | B08-04 |

**（b）什么时候该做 P3 项目而不是 P6**（五问，答"是"≥3 → 做 P3）

| # | 问题 | 答"是"指向 P3 | 答"否"指向 P6 |
|---|---|---|---|
| 1 | 交付物是"业务结论"（为什么涨/跌）吗？ | 是 | 交付物是运行时/评测/沙箱 |
| 2 | 有**可被硬校验的正确答案**（标准 SQL/口径）吗？ | 有，能做 EX | 只有 pass/fail |
| 3 | 需要**领域指标定义**（GMV 含不含退款）吗？ | 需要 | 与业务语义无关 |
| 4 | 核心难点在"语义对齐"而非"调度/上下文/恢复"吗？ | 是 | 在 Harness |
| 5 | 用户是业务方而非开发者吗？ | 业务方 | 开发者 |

> 反过来：若项目 80% 的工程量花在运行时、工具注册、评测门禁上，那就是 P6 项目挂了个"问数"的壳。评审会追问"去掉问数，你的 Harness 还成立吗"。

**（c）"被吸收"的两条机制与应对**

| 机制 | 数据 | 应对 |
|---|---|---|
| 向上被 P6 吸收 | 16 条里 **4 条（25%）本身就是平台内数据子系统**（B08-10、B10-06、B20-08、B21-02），其中 B10-06 的职责就是"Agent 运行框架 + 可观测 + 评测"；B25-07 把 NL2SQL 写进平台路线图 | 项目必须自带**可复现的评测门禁**（EX + 口径一致性 + 归因），把它当作 P3 的"Harness 证据"，而不是 P6 的活儿 |
| 向下被 P1 吸收 | 口径**解释**类需求与 P1 重叠（B25-02 的"提炼数据逻辑和口径"、B25-08 的"指标理解"）；"指标是什么意思"本质是检索题 | 口径**定义**走 P1（RAG），口径**计算**走 P3（编译器），一个项目里分两条链路，不要混成一个问答框 |

**（d）不建议做 P3 独立项目的三种情形**

| 情形 | 判据 | 改做什么 |
|---|---|---|
| 只有 Spider/BIRD 跑分，没有企业口径 | EX 高但口径一致性无法定义 | 补语义层，或改做 P6 的评测子项 |
| 目标是"给 BI 加个对话框" | 前端能力为主 | 做前端 + ChatBI 集成，别当 Data Agent |
| 想做"根因诊断"但没有业务口径 | 输入是日志/指标异常而非业务数据 | 改 **P8**（AIOps 诊断），那里才是根因排序的主场 |

**（e）P3 的扩展方向：从"取数"到"业务洞察"（v2.0 新增判断）**

| 方向 | 原文依据 | 对项目的含义 |
|---|---|---|
| 从"给数"到"给原因" | B08-10 要求"从数据中发现问题、定位原因并提出业务优化建议" | L4 归因要能输出"结构效应/水平效应"之外的**业务语言结论** |
| 从"一次分析"到"可复用技能" | B15-01 "将分析流程沉淀为可复用的 Agent Skill" | 项目要有 Skill 库与复用率指标，而非一次性 prompt |
| 从"问数"到"预测" | B13-03 自然语言查时序 + 解读预测结果 | 加一个预测子集（MAPE），是当前最容易被忽略的差异点 |
| 从"SQL 工具"到"数据工具面" | B25-08 元数据/血缘/质量/调度/权限全部封装 | 工具数量与治理深度，比 SQL 生成准确率更能体现平台思维 |
